# AI summaries

OpenAI-compatible `chat/completions` with `response_format: json_object`. Model from `OPENAI_MODEL` (default `gpt-4o-mini`). No key → `aiEnabled` is false; GET summary reports unavailable; POST returns `AI_UNAVAILABLE`. Everything else in the product still works.

## When a summary exists

Agents click Generate / Refresh on a conversation with at least `aiSummaryMinMessages` (default 6, overridable in workspace settings). Not on inbox open.

Prompt (`PROMPT_VERSION = v1`) asks for three strings only: `userWants`, `tried`, `currentStatus`. Temperature 0, `max_tokens` 500. Output is schema-checked; one stricter retry; then `AI_INVALID_OUTPUT` without wiping a previous good summary.

## Context and cost

Worker loads the last 30 messages, 1,500 characters each, newest first, then trims to ~8,000 tokens using a 4-chars-per-token budget (`trimNewestFirstContext`). No tokenizer on the request path.

Guards on POST, cheap first:

1. Conversation exists in this workspace
2. AI enabled
3. Message threshold
4. Cooldown (60s, 120s after error) and per-conversation Redis cap
5. Workspace daily cap (200)

The job is queued only after those pass. In-flight duplicate: DB row already `QUEUED`. The QUEUED transition itself (`repo.tryMarkQueued`) is one atomic `INSERT ... ON CONFLICT DO UPDATE ... WHERE NOT (already QUEUED and fresh)`, not a separate read-then-write — two near-simultaneous triggers for the same conversation would otherwise both pass the earlier checks and both enqueue a job, and whichever job's transaction committed last would overwrite the other's `sourceMessageCount`/`sourceLastMessageId`, corrupting the staleness watermark `getSummary()` relies on. Only the request that wins the atomic transition enqueues; the loser gets the same idempotent "queued" response. Job ids are unique per enqueue (`ai-summary:{id}:{timestamp}`) because BullMQ would otherwise no-op a reused id.

## Failure modes

- HTTP timeout 30s (`AbortController`)
- BullMQ: 3 attempts, backoff
- Abandoned `QUEUED` older than 240s is shown as error so Retry appears
- Dashboard also polls every 2s while `queued` in case a socket emit is missed

States the UI understands: `below_threshold`, `eligible`, `queued`, `ready`, `stale`, `error`.
